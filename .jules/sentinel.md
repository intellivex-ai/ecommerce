## 2026-04-15 - [Fix Authorization Bypass in Frontend and Database RLS]
**Vulnerability:** The application was using brittle string comparison against the user's name (e.g. `profile?.full_name === 'Admin'`) to control access to the admin panel UI. The database schema's RLS policies were also loosely restricting updates based on checking `auth.uid() = id`, but did not securely protect role escalation, potentially allowing a user to change their role status if an `is_admin` column were casually added. There was no true role-based protection on routes or database access.
**Learning:** Frontend UI checks alone are insufficient for security, especially when relying on mutable or easily spoofed fields like a display name. Additionally, a robust RLS policy must strictly prevent users from escalating their own privileges via `WITH CHECK` constraints on sensitive boolean role flags.
**Prevention:** Implement a dedicated, securely managed `is_admin` boolean column in the `profiles` table that defaults to `false` and cannot be modified by the user themselves through restrictive RLS policies (e.g., using a `WITH CHECK` clause that ensures the `is_admin` value being set matches the user's current `is_admin` state). Use this boolean flag for both frontend route protection (e.g., via an `AdminRoute` component) and conditional UI rendering, rather than relying on unverified string names.
