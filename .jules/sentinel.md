## 2024-05-24 - Overly Permissive RLS Policies allowing unauthorized data manipulation
**Vulnerability:** Discovered multiple critical RLS misconfigurations in `database_schema.sql` where `products` allowed arbitrary public INSERT/UPDATE/DELETE due to `with check (true)` and `using (true)`. Additionally, the `orders` table allowed public updates, and the `profiles` table lacked a mechanism to prevent users from escalating their privileges if an `is_admin` column was introduced.
**Learning:** Initial schema definitions often default to highly permissive RLS policies during prototyping but fail to secure endpoints prior to deployment. Furthermore, when defining `profiles` policies that allow users to update their own profile, it is critical to explicitly prevent modification of sensitive roles/flags via a `WITH CHECK` constraint to avoid privilege escalation.
**Prevention:** Always implement a concrete `is_admin` or role-based check for write policies on global entities (like `products` and `orders`). For self-updateable tables like `profiles`, always apply a `with check (is_admin = (select is_admin from public.profiles where id = auth.uid()))` to lock down sensitive fields from user manipulation.
